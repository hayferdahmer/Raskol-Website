# Энциклопедия РАСКОЛА — архитектура

**Статус:** проектирование контента и данных  
**Цель:** единый справочник игровых сущностей без копирования карточек вручную по разным страницам.

## Разделы

- Классы и специализации — ссылки на утверждённый каталог классов.
- Предметы и экипировка — слот, редкость, требования, источник получения.
- Способности и таланты — класс, специализация, ресурс, описание.
- NPC и существа — тип, регион, фракция, поведение.
- Ресурсы и материалы — категория, профессия, способы добычи.
- Подземелья и активности — уровень/допуск, режим, награды.
- Репутации и достижения — условия и награды после утверждения механик.

## Принцип данных

Контент хранится отдельно от разметки. Каждая запись имеет стабильный slug, тип, название, краткое описание, статус публикации и ссылки на связанные сущности. UI строится общими шаблонами: каталог, фильтр, карточка и подробная страница.

Рекомендуемая структура будущей реализации:

```text
encyclopedia/
  index.html
  items/index.html
  abilities/index.html
  creatures/index.html
  dungeons/index.html
assets/
  data/
    encyclopedia/
      manifest.json
      items.json
      abilities.json
      creatures.json
      dungeons.json
```

## Минимальная модель записи

- `id`: стабильный slug, не меняется при переименовании.
- `type`: тип сущности из закрытого перечня.
- `name`: публичное название.
- `summary`: короткое описание.
- `description`: подробное описание, Markdown только после безопасной обработки.
- `icon`: относительный путь к локальному ассету; внешние URL не принимаются автоматически.
- `tags`: массив фильтров.
- `status`: `draft`, `review`, `published`, `archived`.
- `source`: ссылка на подтверждающий игровой источник/решение.
- `updatedAt`: дата редакционного обновления.

Типоспецифичные данные размещаются в отдельном объекте `details`. Например, предмет может иметь `slot`, `rarity`, `requiredLevel`, но нельзя добавлять характеристики, пока они не подтверждены в игре.

## Редакционные ограничения

- Не придумывать характеристики, drop rates, цены, уровни, бонусы и способы получения.
- Не выдавать запланированные механики за работающие.
- Не копировать описания классов, если каноническая страница уже существует: использовать ссылку и единый источник.
- Не показывать черновые записи в публичном поиске.
- У каждой опубликованной записи должен быть владелец контента и подтверждённый источник.

## Поиск и фильтрация

Первый этап — клиентский поиск по локальным JSON-данным: название, slug, описание и теги. Фильтры должны работать без перезагрузки и поддерживать URL query params. При росте каталога можно перейти на индексированный поиск, сохранив формат данных.

## Производительность и доступность

- Разбивать каталог по типам, не загружать весь справочник на каждую страницу.
- Использовать lazy loading изображений и фиксированные размеры медиа.
- Все фильтры доступны с клавиатуры, имеют label и видимый focus.
- Состояния: загрузка, пустая выдача, ошибка данных, нет результатов.
- На мобильных фильтры не должны перекрывать весь экран без понятного закрытия.

## Этапы

1. Согласовать схему и процесс публикации.
2. Заполнить подтверждённые данные классов и специализаций из действующих страниц.
3. Добавить каталог предметов после выгрузки/подтверждения данных игрового сервера.
4. Добавить существа, активности и взаимосвязи.
5. Связать сущности с конструктором персонажа.

Эта архитектура не утверждает наличие всех перечисленных игровых механик.
